## Project Truss scientific-computing contract

Treat the repository as an executable scientific argument. Work flows from a scientific question to falsifiable claims, traceable sources and inputs, a declared formulation, numerical experiments or benchmarks, implementation only when needed, scientific review, and an evidence-backed GitHub closeout.

Discovery does not create missing directories or declare scientific authority. Each durable benchmark names its claim family, source, oracle independence, inputs, tolerance basis, certificates, failure meaning, and provenance. Change-detection snapshots may guard a locked artifact but are not independent scientific oracles.

### Numerical verification doctrine

- State the claim and how it could be falsified before implementation.
- Resolve units, conventions, source provenance, model version, valid domain, and justified tolerances.
- Prefer independent references, identities, limits, residual certificates, metamorphic relations, manufactured solutions, convergence studies, literature reproductions, or experimental data.
- Use test-driven development only for an explicitly durable discrete software contract. Scientific uncertainty is resolved through research, derivation, and numerical experiments.
- Keep exploratory lab artifacts nonpersistent unless intentionally promoted. Preserve retired scientific work in Git history rather than compatibility scaffolding.
- A well-supported `FALSIFIED` result is a successful scientific outcome. Do not turn a negative result into a failed workflow.

### Evidence packet

Closeout records the claim ID, classification, source locators, assumptions, model and input revisions, exact command and environment, raw-result artifacts, comparisons with tolerance bases, certificates, limitations, artifact hashes, and separate judgments for source, formulation, numerical verification, empirical validation, reproducibility, and implementation promotion.
